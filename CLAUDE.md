# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Commands

```bash
npm run dev          # Next.js app (port 3000)
npm run worker       # Background task worker (separate process, required for tasks to run)
npm run lint         # ESLint
npm run build        # Production build
npm run db:migrate   # Run Prisma migrations (after schema changes)
npm run db:generate  # Regenerate Prisma client (after schema changes)
```

Both `dev` and `worker` must run simultaneously for the full system to work. The worker polls the DB every 5s for pending tasks.

## Architecture

This is a task queue that runs Claude agents against Git repos. The system has two runtime processes:

**Next.js app** — UI + REST API. All routes are under `src/app/api/`. Pages are server components that read from DB directly via `src/lib/db.ts` (Prisma + SQLite via better-sqlite3 adapter). Client components poll or use SSE for live updates.

**Worker** (`src/worker/index.ts`) — Long-running Node process. Polls for `pending`/`paused` tasks, clones repos into `/workspaces/{taskId}/{alias}/`, spawns `claude -p <prompt>` with `cwd` set to the workspace root, streams output to `TaskLog`, then commits and pushes a branch. The worker is the only process that mutates task status to `running`/`completed`/`failed`.

### Key data flows

- Task creation: `POST /api/tasks` → DB insert → worker picks it up on next poll
- Live logs: `GET /api/tasks/[id]/logs/stream` → SSE route that polls `TaskLog` every 500ms
- User messages mid-task: `POST /api/tasks/[id]/message` → inserts `TaskMessage`; worker's `getNextMessage()` polls and injects them into the claude CLI session
- Repo Q&A ("Ask" on the Repositories page): `/repositories/chat?url=…` loads a snapshot of the repo once via `POST /api/tasks/git-context` (shallow clone → tree + README + manifests + top-scoring source files), caches it in `sessionStorage`, then replays it with each turn to `POST /api/repos/chat`. Read-only — see `src/lib/repo-chat.ts`; it never proposes or creates a task, and runs the CLI provider with `--tools ""`.
- Per-repo task defaults: a repo saved on the Repositories page can carry defaults for everything in the new-task form's "Advanced Options" (priority, effort, budgets, provider/model, labels, follow-up validation task) plus a default context. Stored as JSON in the `saved_repo_presets` Setting row — see `src/lib/repos.ts`. They're applied in two places: the new-task form prefills them when a repo is picked, and `POST /api/tasks` fills in any field the caller omitted via `resolveRepoDefaults()` (so webhooks/email/Slack inherit them too). A value the caller passes explicitly — including `null`, which the form sends for options the user deliberately cleared — always beats the repo default.
- Per-repo git defaults: the same blob can hold `defaultBranch` (clone/base branch) and `defaultGitMode` (`branch`/`target`/`main`/`pr` — the "After task completes" choice) plus `defaultTargetBranch` for `target`. The branch is per repo (`resolveRepoBranches()` fills each repo the caller sent without a branch); the mode is task-level (first repo with one wins, together with its target branch) and only applies when the caller set none of `pushToMain`/`createPR`/`targetBranch`. `POST /api/tasks`, `POST /api/v1/tasks`, webhooks and inbound email all apply them; the new-task form prefills them when a repo is picked, but never overrides an "After task completes" option the user already chose.
- Per-repo default team: the same blob can hold `defaultTeamId`, set on the Repositories page ("Run tasks with a team by default"). When a task names no team (`teamId` omitted), `POST /api/tasks`, `POST /api/v1/tasks`/MCP `create_task`, webhooks and inbound email give it the first of its repos' default team; an explicit `teamId: null` (the new-task form sends it when the user switched "Use a team" off) opts out. A team deleted after being saved as a default is dropped via `existingTeamId()` (`src/lib/teams.ts`), so the task runs as a single agent instead of failing. The new-task form switches "Use a team" on with the repo's team when the repo is picked, unless the user already touched the team toggle.
- Per-repo concurrency limits: a saved repo can also set `maxConcurrentTasks` (absent = unlimited), stored in the same `saved_repo_presets` blob. Unlike the `default*` fields it is *not* copied onto tasks — the worker enforces it at pick-up time on every poll, so changing it takes effect for already-queued tasks. See `src/lib/repo-concurrency.ts`: repos are matched by normalized scope (the SSH and HTTPS URLs of one repo share a limit), a task needs a free slot on *every* repo it touches, and a task held back by a full repo is skipped rather than blocking the tasks queued behind it. The global `concurrent_tasks` setting still caps the total.
- Recurring tasks: worker checks cron expressions on each poll cycle, spawns new task instances from templates. A template can cap how many times it fires via `maxRuns` (null = unlimited, the default); the worker increments `runCount` on every cron-triggered spawn and stops once `runCount >= maxRuns` (see `src/lib/max-runs.ts`). Manual "Run now" and Hail Mary bursts don't count toward the cap.
- Team pipelines: a task can be assigned a `Team` (`Task.teamId`) instead of running as a single agent — see the "Use a team" toggle on the new-task form and the `/teams` management page. A Team is an ordered list of `TeamMember` rows (name/role + free-text instructions + `position`), managed via `src/lib/teams.ts` and `/api/teams*` (drag-and-drop reordering persists immediately through `POST /api/teams/[id]/members/reorder`, mirroring `POST /api/tasks/reorder`). The worker only looks up the roster at run time (not a snapshot on the task), so editing a team after task creation still applies next run. Execution is in `runTeamPipeline()` in `src/worker/index.ts`: members run strictly in `position` order, each stage's prompt carries the previous stage's output forward plus its own instructions, and a failed stage stops the pipeline immediately (surfaced as an "error"-level log naming the stage) rather than continuing silently. Every log line a stage produces is stamped with the member's name (`TaskLog.member`, passed as the 4th arg of the worker's `log()`), which the activity log shows as a prefix badge and can filter by; diagnose/verify/progress-summary, resume `priorLogs` and the MCP/v1 log outputs carry it too (`memberLogPrefix()`). Stage state is recorded as JSON in `Task.teamProgress` at every transition (`startTeamProgress`/`markStage*` in `src/lib/team-progress.ts`, pure, unit-tested) and rendered by the "Team progress" tracker on the task page (`TeamProgressTracker`, polling `GET /api/tasks/[id]/team-progress`); `buildTeamProgressView()` reconciles it with the task status, so a stage left `running` shows as paused (rate limit / auth hand-off, which deliberately don't mark it failed) or interrupted (killed/timed out). Re-queueing via `PATCH status: "pending"` clears it along with the logs. **Manual approval gates:** a member with `TeamMember.requiresApproval` ("Wait for my approval before the next member" on `/teams`, e.g. a Planner) stops the pipeline once it finishes — unless it's the last member — with the stage recorded as `awaiting_approval` (its output and token counts stored on the stage) and the task in the `awaiting_approval` status (In Progress column; not picked up by the worker; nothing is committed or pushed yet). The tracker shows the output with "Approve & continue" / "Request changes", which call `POST /api/tasks/[id]/team-approval` (`{ decision: "approve" | "revise", feedback? }`, also MCP `approve_team_stage`) → `decideTeamApproval()` in `src/lib/task-actions.ts`: it records the decision on `teamProgress` (`approveStage`/`requestStageRevision`) and re-queues the task with `retryCount` bumped so the workspace is reused. The next run's `runTeamPipeline()` uses `planTeamResume()` to skip the stages before the decision — the next member gets the approved output plus the approver's notes, a revised stage gets the feedback and its previous output — and seeds the token totals from the stored stages; with no decision, or a roster that no longer matches the completed stages, it starts from the first member as before. All repo/branch/commit/PR handling in `runTask()` is unchanged and shared with single-agent tasks — only the "spawn the agent and get a result" step branches on `teamId`.
- Slack task proposals: when the bot calls `propose_task` it posts a *form*, not just a confirmation — provider/model, schedule (run now / date+time pickers / cron + max runs), repos and their branches, git output (new branch / existing branch / push to main / open a PR) and a context field, then "Create Task"/"Cancel". Anything the model filled in only pre-fills the form. Every widget writes straight back onto the proposal JSON in `SlackConversation.proposed`, which is the single source of truth the approve button reads — there's no draft state elsewhere. The pure state/block helpers live in `src/lib/slack-proposal.ts` (unit-tested); `src/integrations/slack.ts` keeps the I/O (block rendering, Bolt action handlers, DB). Two things worth knowing before editing: block ids encode the thread (`kind__[index__]threadTs`) so handlers can find the conversation from any widget, and single-line inputs save on Enter while the multi-line context field is read from the message `state` Slack sends with every interaction (including the "Create Task" click).
- Slack provider fallback: every provider id Slack holds — the one pinned in Settings → Integrations, and the one stored on a proposal — is a *stale id* by the time it's used, because the provider it names can be disabled, deleted or rate-limited in the meantime. None of those may break the bot. Chat turns resolve through `getProvider()` (the same chain the worker uses, so a disabled pin falls through to smart pick → default → any enabled provider), and the proposal form resolves through `pickProposalProvider()` in `src/lib/slack-provider.ts` (unit-tested, pure). Disabled providers are never selected; a rate-limited one still is when it's all that's left, since the task runs later. Three rules to keep in mind when editing: the substitution is written back onto `SlackConversation.proposed` so the form and the created task can't disagree, it is re-checked on the "Create Task" click (pinning nothing when nothing is enabled, letting the worker resolve at run time), and a model override only survives a substitution when it fits the new provider's vendor — `modelFitsProvider()` stops a `gpt-*` id being sent to an Anthropic connection.
- Agent-created subtasks: Advanced Options → "Allow agent to create subtasks" (`Task.allowSubtasks`; also `allowSubtasks` on `POST /api/tasks` / `POST /api/v1/tasks`, and a per-repo default `defaultAllowSubtasks`) lets an agent fan work out, e.g. "go through each exam and create a task to clean up its questions". The agent has no DB/API access, so the hand-off is a file: the worker appends a "Creating Subtasks" section to the system prompt (team stages too) telling it to write a JSON array to `.subtasks.json` at the workspace root (outside every repo, so never committed). After a successful run (`completed` or `no_changes`), `createRequestedSubtasks()` in `src/worker/index.ts` parses it with `parseSubtaskRequests()` (`src/lib/subtasks.ts`, pure, unit-tested), creates one Task per entry with `parentTaskId` set — inheriting the parent's repos (or the subset named), provider/model, priority, effort, tool access, team, labels, budgets and PR/push mode, but never `targetBranch` or `allowSubtasks`, so fan-out is one level deep — and renames the file to `.subtasks.processed.json` so a retry doesn't duplicate them. `dependsOnPrevious: true` chains a subtask after the one before it. Capped at 50 per run. The task detail page lists a task's parent and subtasks. Rebase-only and PR-review runs never get the option.
- Review-only tickets: `Task.reviewOnly` is a reminder to review work done elsewhere (a hand-pushed commit, another Claude session). It's created straight into In Review (`status: "completed"`, `reviewStatus: "in_review"`) via `reviewOnly: true` on `POST /api/tasks`, `POST /api/v1/tasks` and MCP `create_task`, or the "Review only" tab on the new-task page (`ReviewTaskForm`), and **never runs**: the worker's pick-up query is `runnableTaskWhere()` (excludes it), `runTask()` returns early for one, and every re-queue path (start, re-run/PATCH `status`, message, request-change, review-pr, rebase, bulk-retry, Slack) refuses it with `REVIEW_ONLY_RUN_REFUSAL`. Review decisions: approve → Done and reopen → In Review as usual; **request changes is refused** (`REVIEW_ONLY_CHANGES_REFUSAL`) — there's no agent run to continue, so the reviewer creates a normal task on the branch. Optional review metadata — repo (saved repo or any Git URL), branch, commit SHAs (7–40 hex, stored as given as a JSON array) and an http(s) PR link — lives in `reviewRepo`/`reviewBranch`/`reviewCommits`/`reviewPrUrl`, is validated by the pure `parseReviewMetadata()` (errors name the field, e.g. `reviewMetadata.commits`) and edited via `reviewMetadata` on create, PATCH `/api/tasks/[id]`, `PATCH /api/v1/tasks/[id]` and MCP `update_task` (`planTaskEdit()` only allows ticket fields on one). Search by commit SHA / PR URL is `reviewSearchClauses()` (list_tasks, `GET /api/tasks?q=`, `GET /api/v1/tasks?q=`). The task page shows a "To review" card (`ReviewMetadataDetails`) with GitHub links, one-click SHA copy and the PR's state from `gh pr view` (`fetchReviewPrState()` in `src/lib/review-pr-state.ts`, best effort, parsed by the pure `parseGhPrView()`). Pure logic is `src/lib/review-only.ts` (unit-tested in `review-only.test.ts`).
- Agent tool access: which external CLIs an agent may use (currently the GitHub CLI, `gh`; built to take more, e.g. the AWS CLI). Settings → Agent Tools (`/settings/tools`) stores each tool's credentials (`github_cli_token`, or `github_cli_use_git_token` to fall back to the Git PAT) and whether it's granted by default (`agent_tool_defaults`, JSON map tool id → boolean). A task can override any tool either way via `Task.toolAccess` (JSON map; tools left out follow the default *at run time*, so already-queued tasks see default changes), set from Advanced Options → Tool Access on the new/edit task forms or `toolAccess` on `POST /api/tasks` / `POST /api/v1/tasks`. The pure half (registry, resolution, env overlay, prompt section) is `src/lib/agent-tools.ts` (unit-tested); the worker half is `prepareAgentTools()` in `src/lib/agent-tools-runtime.ts`, called in `runTask()` just before the provider is created. It returns an `AgentEnvOverlay` that every provider applies to what it spawns (`provider.agentEnv` — the `claude`/`codex` child env, and `executeTool()`'s bash for the API providers): granted tools get their token (`GH_TOKEN`/`GITHUB_TOKEN`); every tool's credential env vars are stripped from the inherited env first; denied tools get a PATH shim that prints "access not granted"; and `GH_CONFIG_DIR` always points at an empty per-run temp dir, so a `gh auth login` on the worker host is never visible to agents. A matching "External Tool Access" section is appended to the system prompt (including team stages). To add a tool: registry entry in `AGENT_TOOLS` (secret keys there are auto-masked by `GET /api/settings`), a branch in `prepareAgentTools()`, and a card on the settings page.
- LLM gateway (OpenAI/Anthropic-compatible): `/api/llm/v1/chat/completions` (OpenAI), `/api/llm/v1/messages` (+ `/count_tokens`) (Anthropic) and `/api/llm/v1/models` let any tool built for either API set its base URL to `<origin>/api/llm/v1` (OpenAI) or `<origin>/api/llm` (Anthropic) and run on the provider `getProvider()` resolves from the *API key's* provider choice — `ApiKey.aiProviderId` (pinned connection) / `ApiKey.useSmartProvider`, set from the picker in Settings → API when creating a key or later per key (`provider: id | "smart" | ""` on `POST`/`PATCH /api/api-keys`, parsed by the pure `src/lib/api-key-provider.ts`); neither = smart pick if globally on → default → any enabled, and a disabled/deleted/throttled pin falls through the same chain. Auth is a normal `tm_live_` API key sent as `Authorization: Bearer` or `x-api-key` (`findApiKey()` in `src/lib/api-auth.ts`, which also returns the key's provider choice). A request whose format matches the provider's API is passed through (Anthropic → `api`/`claude-pki`, OpenAI → `openai`); a mismatch is translated by the pure `src/lib/llm-gateway/convert.ts` (unit-tested), which pivots on Anthropic messages/stream events — sampling params and forced `tool_choice` are dropped on the way to Claude because current models 400 on them. Subscription CLIs are text-only: `claude -p` runs with `--tools ""` and `--include-partial-messages`, whose `stream_event` lines *are* Anthropic stream events, so it streams for real; Codex answers in one burst. Client tools on a CLI provider are *emulated* (pure, in `routing.ts`): `buildCliPrompt()` describes them in the system prompt and replays earlier `tool_use`/`tool_result` blocks as `<tool_call>`/`<tool_result>` tags, and `applyCliToolCalls()` parses the model's `<tool_call>` blocks back into `tool_use` blocks with `stop_reason: "tool_use"` — so a request with tools is buffered and replayed rather than streamed. The Claude CLI also gets images/PDFs as a stream-json user message on stdin, `web_search`/`web_fetch` server tools mapped onto its built-in `WebSearch`/`WebFetch` (`--tools` + `--allowedTools`), and every enabled MCP server from Settings → MCP Servers (`prepareGatewayMcp()`, Codex too). Once the CLI runs its own tools, one request is several API turns; `CliTurnMerger` (convert.ts) folds them into one message and hides the internal `tool_use` blocks. Other server tools, and media on Codex, are a 400, not silently ignored. Which requested model is honoured is `resolveGatewayModel()` (`src/lib/llm-gateway/routing.ts`): the other vendor's ids and `default` fall back to the provider's own model. Every request's token usage is persisted as an `LlmGatewayUsage` row (`recordGatewayUsage()` in `src/lib/llm-gateway/usage-record.ts`, called from `GatewayCall.finish()`, fire-and-forget) — /analytics' "Token Spend by Source" card compares it with task-run tokens via the pure `buildTokenSpendBreakdown()` (`src/lib/token-spend.ts`, unit-tested). The "API Proxy" analytics tab (`/analytics/gateway`, tabs via `AnalyticsTabs`) breaks gateway usage down by time (last 24h hourly, daily, hour of day), model, API key and request via the pure `buildGatewayAnalytics()` (`src/lib/gateway-analytics.ts`, unit-tested); its estimated cost prices subscription-CLI usage at API rates (`gatewayRowCost()`), kept apart from the billed figure. The gateway can be **temporarily disabled** ("Disable temporarily" on that tab and in Settings → API, `GatewayPauseControl` → `GET`/`PUT {duration}`/`DELETE /api/gateway-pause`): the `llm_gateway_paused_until` Setting holds an ISO time or `indefinite` (pure parsing in `src/lib/llm-gateway/pause.ts`, unit-tested; DB in `pause-store.ts`), and `authenticateGateway()` answers every authenticated request with a 503 (+ `Retry-After`) while it's in the future — a timed pause ends on its own, no job involved. Runtime is `src/lib/llm-gateway/backends.ts`; errors come back in each API's own envelope, and mid-stream failures as an SSE error event. User-facing docs are `/docs/llm-gateway` (text in `src/lib/docs-content/llm-gateway.ts`, linked from Settings → API) — update it when the behaviour changes.
- MCP server: `/api/mcp` is a Model Context Protocol endpoint (Streamable HTTP, **stateless** — every request is a POST with one JSON-RPC message, answered with plain JSON; GET/DELETE return 405) so assistants like Claude Code/Desktop, Cursor and VS Code can query and drive tasks. Clients authenticate with `Authorization: Bearer tm_mcp_…` tokens from Settings → MCP (`/settings/mcp`, `McpToken` model, CRUD at `/api/mcp-tokens*`; only the SHA-256 hash is stored, like `ApiKey`, and the two credential types never work in place of each other). Each token is `read` or `write`: access is enforced centrally in `src/lib/mcp/protocol.ts` (pure, unit-tested JSON-RPC dispatch) — a tool declares the access it needs, and a read-only token neither sees write tools in `tools/list` nor can call them. Tools and prompts live in `src/lib/mcp/tools.ts`: read tools (`list_tasks` — `recurringTemplates: true` lists recurring templates instead, `get_task`, `get_task_logs`, `get_task_stats`, `list_task_files`, `read_task_file`, `list_repositories`, `list_teams`, `list_providers` — never returns credentials, `get_docs` — the /docs pages as markdown with this deployment's URLs) and write tools (`create_task`, `update_task`, `start_task`, `cancel_task`, `approve_team_stage`, `send_task_message`, `review_task`). Write tools go through `src/lib/task-actions.ts`, the same functions behind `POST /api/v1/tasks`, the v1 start route and the kill/message/request-change routes, so MCP behaves exactly like the UI — add new shared mutations there rather than inline in a route. `update_task` mirrors the edit form's `PATCH /api/tasks/[id]` (git mode/target branch, repos and per-repo `repoBranches`, team, dependency, budgets, tool access, …) plus `provider` (connection id / `"smart"` / `""`; disabled connections and vendor-mismatched models are rejected) and, for recurring templates, `cronExpression`/`maxRuns`/`resetRunCount` (a changed schedule is counted from now via `lastScheduledAt`), and takes `ids` for an all-or-nothing bulk edit; `create_task` takes `provider` too, and `cronExpression` makes it a recurring template; its argument→column logic is the pure `planTaskEdit()` in `src/lib/mcp/task-update.ts` (unit-tested) — when the edit form gains a field, add it there too. Deleting tasks and editing settings are deliberately not exposed. Expected tool failures throw `McpToolError` (returned as an `isError` result the model can read). The `/docs/mcp` page renders its tools reference straight from `MCP_TOOLS`, so adding a tool documents it (on the page and in `get_docs`); the prose of every /docs page lives in `src/lib/docs-content/*` (inline-markdown strings rendered by `<Prose>` on the page and passed through as markdown by `get_docs`, topics registered in `DOCS_TOPICS`), so edit docs text there, not in the page components; client setup snippets come from `src/lib/mcp/client-config.ts`. The same markdown feeds the /docs search box (⌘K / Ctrl+K on any /docs page, `<DocsSearch>` in the docs layout; on /docs it takes the shortcut over from the nav's task search): `docsSearchIndex()` splits each topic at its headings and the pure `src/lib/docs-search.ts` (unit-tested) ranks sections client-side. Each topic's `anchors` maps its `##` headings to the page's section ids — a test fails if a new `##` heading has no entry; deeper headings with their own id on the page (each MCP tool and use case) come from `subAnchors` (`mcpSubAnchors()`), the rest inherit their parent's anchor.
- MCP OAuth: so Claude Code, Claude Desktop (custom connectors / `mcp-remote`), Codex, VS Code and Cursor can connect with nothing but the URL, `/api/mcp` is also an OAuth 2.1 protected resource. Its 401 carries `WWW-Authenticate: Bearer resource_metadata=…` → `/.well-known/oauth-protected-resource[/api/mcp]` (RFC 9728) → `/.well-known/oauth-authorization-server` (RFC 8414) → dynamic client registration `POST /api/oauth/register` (`OAuthClient`) → consent page `/oauth/authorize` (server component; the form posts to `POST /api/oauth/authorize`, which re-validates everything and refuses cross-site posts) → `POST /api/oauth/token` (`authorization_code` with mandatory PKCE S256, `refresh_token`) and `POST /api/oauth/revoke`. A grant *is* a `McpToken` row (`oauthClientId`, `expiresAt` = 1h access token, rotating `refreshTokenHash`/`refreshExpiresAt` = 30d sliding), so `authenticateMcpRequest()` only adds an expiry check, and the grant appears in Settings → MCP with an OAuth badge where its access can be changed or it can be revoked. Codes (`OAuthAuthCode`) are hashed and single-use. The consent page requires a signed-in session (see Authentication), so only someone who can sign in can approve. Pure rules (metadata, PKCE, redirect-URI/scope/resource checks, request parsing) are `src/lib/mcp/oauth.ts` (unit-tested); DB is `src/lib/mcp/oauth-store.ts`; public origin comes from `requestOrigin()` (`src/lib/request-origin.ts`).
- External MCP servers for agents (the other direction from the MCP endpoint above): Settings → MCP Servers (`/settings/mcp-servers`, `McpServer` model, CRUD at `/api/mcp-servers*`) lists MCP servers agents can call — `stdio` (command + args + env, started on the worker host), `http` (Streamable HTTP) or `sse` (URL + headers). Env and header values are secrets: the API masks them and sending the mask back on update keeps the stored value (`mergeSecrets()`). Every **enabled** server is attached to every task run, read at run time, so edits apply from the next run. The pure half (validation, masking, config builders, prompt section) is `src/lib/mcp-servers.ts` (unit-tested); the worker half is `prepareMcpServers()` in `src/lib/mcp-servers-runtime.ts`, called in `runTask()` right after `prepareAgentTools()`. It returns `provider.mcp` (set via `createProvider({ mcp })`): the Claude CLI gets `--mcp-config <file>` pointing at a 0600 JSON file in a per-run temp dir (never inside the workspace, so secrets can't be committed; additive to any `.mcp.json` in the repos), and Codex gets `--config mcp_servers.<name>.…` overrides (SSE servers are skipped — Codex doesn't support them). API-based providers run their own tool loop and get none; the task log says so. A "MCP Servers" prompt section lists the attached servers (team stages too). Preparing them can't fail a task — errors are logged and the run continues without MCP.

- Email delivery: every outgoing email (task notifications, provider alerts, low-usage warnings, file-deletion notices, replies to inbound-email tasks, the "Send test" button) goes through `sendEmail()` in `src/lib/notifications.ts` with a transport resolved by the pure `resolveEmailTransport()` (`src/lib/email-transport.ts`, unit-tested) from Settings → Notifications → Email delivery (`EmailDeliveryCard`): `email_transport` = `smtp` (nodemailer; `smtp_host`/`smtp_port`/`smtp_security` starttls|tls|none/`smtp_username`/`smtp_password`) or `ses` (`ses_credential_source` env|settings, `ses_region`, `ses_access_key_id`/`ses_secret_access_key`), plus the sender `notification_from_address`. Nothing is sent until a method and sender are set (`kind: "none"` carries the reason, which the notification functions return as "not sent"); the one fallback is an install that never chose a method but has AWS keys in its environment, which keeps using SES as before. `smtp_password`/`ses_secret_access_key` are masked by `GET /api/settings`, and posting the mask back keeps the stored value. `GET /api/notifications/email-status` tells the card whether the environment has AWS keys and what the config resolves to. Notification links use the `app_host` Setting, defaulting to `localhost:3000` (`DEFAULT_APP_HOST`, `src/lib/app-host.ts`).

### Authentication

Sign-in is optional: the `auth_required` Setting (Settings → Security → "Require sign-in", `GET`/`PUT /api/auth/required`, read by `authRequired()` in `src/lib/auth/http.ts`, parsed by the pure `parseAuthRequired()`) is **off when missing**, so fresh installs open straight into the app; the `add_auth_required_setting` migration turns it on for installs that already had sessions, passkeys or a changed password. While it's off the proxy lets every request through and the root layout renders the full app with a "Sign in" link instead of the user menu (`/login` still works, and turning it on requires a session — `checkAuthRequiredToggle()` — so nobody locks themselves out); Settings → Account/Security show a sign-in prompt for the account-specific parts, whose routes still use `requireSession()`. While it's on: every request goes through `src/proxy.ts` (Next 16's renamed middleware, Node runtime, so it reads the DB): without a valid `tm_session` cookie, pages redirect to `/login?next=…` and API routes get a 401. `isPublicPath()` in `src/lib/auth/policy.ts` (pure, unit-tested in `auth-policy.test.ts`) is the allow-list — sign-in pages/endpoints, static assets, and routes that check their own credential (`/api/v1/*`, `/api/llm/*`, `/api/mcp`, OAuth token/register/revoke, `/.well-known/*`, `/api/webhooks/receive/*`, `/api/integrations/email/inbound`). **A new route that authenticates some other way must be added there; everything else is protected automatically.** The worker and integrations talk to the DB directly, never over HTTP, so they're unaffected.

The app stays single-tenant: `User` rows gate access, they don't own data. Sessions (`Session`, SHA-256 of a random cookie token, 30 days), passwords (scrypt, `src/lib/auth/password.ts`), passkeys (`Passkey`, `@simplewebauthn/server` in `src/lib/auth/webauthn.ts`, challenges in `AuthChallenge` referenced by a cookie; browser half in `webauthn-client.ts`, no client library) and the audit trail (`SignInEvent` via `recordAuthEvent()`) live under `src/lib/auth/`; routes are `/api/auth/*`. `User.passwordLoginDisabled` = passkey-only; it can only be set while the user has a passkey, and deleting the last passkey clears it (`passwordLoginAllowed()` also ignores it when no passkey exists). Sign-ups are the `auth_signups_enabled` Setting (default off, toggled via `PUT /api/auth/signups`). Sign-in is optional (`auth_required` Setting, off on fresh installs; Settings → Security → "Require sign-in"). The `add_auth` migration seeds a placeholder account `admin@example.com` with password `changeme` and `mustChangePassword`, which drives a header banner; `scripts/reset-password.ts <email> <password>` creates or resets a real account from a shell. UI: `/login`, `/signup`, Settings → Account (password, passkeys, password sign-in toggle, sessions) and Settings → Security (sign-ups, accounts, sign-in log). Server components read the user with `getCurrentSession()`; route handlers that need it call `requireSession(req)`. The root layout renders a bare shell (no nav or polling widgets) when signed out.

### Observability (OpenTelemetry)

Traces, metrics and logs can be exported over OTLP (HTTP protobuf, HTTP JSON or gRPC), configured entirely from Settings → Observability and stored as `otel_*` Setting rows. Export can fan out to several **destinations** (e.g. a self-hosted collector and a SaaS backend at once): each has its own endpoint, protocol, headers and per-signal toggles, and the list is stored as JSON in `otel_destinations`, edited through `/api/settings/otel/destinations` (which masks headers; the generic `GET /api/settings` masks the whole blob). A signal reaches a destination only when it's on globally *and* for that destination — `exportTargets()` is the one place that decides. Until the list is first saved, the old single-collector keys (`otel_endpoint`/`otel_protocol`/`otel_headers`) stand in as one destination; the first save deletes them. The runtime gives each destination its own span processor / metric reader / log processor, so a dead backend can't stall the others, and failed exports are logged with the destination's name. The Claude CLI only takes one endpoint, so "Forward to Claude Code" uses `agentDestination()` (the chosen one, else the first usable). `src/lib/otel-config.ts` is the pure half (parsing, URLs, the Claude CLI env; unit-tested) and `src/lib/otel.ts` the runtime. Each process calls `initTelemetry()` once — the app from `src/instrumentation.ts`, the worker and integrations from their `main()` — and it re-reads the settings on a poll (15s worker, 30s otherwise; `POST /api/settings` reloads the app instantly for `otel_*` keys). When the config fingerprint changes, the providers are torn down and rebuilt, so the on/off switch never needs a restart.

Because of that hot swap, never hold on to SDK objects: a *delegating* TracerProvider is registered globally once (it's also what Next.js's built-in request spans go through), `getMeter()` must be called per use, and observable instruments go through `onMeterReady()` so they're re-registered after a reload. Worker instrumentation lives in `src/worker/telemetry.ts`: the main loop wraps each `runTask()` in `traceTaskRun()` (a `task.run` span plus `ctm.*` metrics read back from the finished task row — deliberately not threaded through `runTask()`'s many return paths), `withTaskSpan()` adds `invoke_agent` children (one per team stage), and the worker's `log()` mirrors every TaskLog line as a log record correlated with the task's span. Optional console capture patches `console.*`; OTel's own diagnostics go to the *unpatched* console, rate-limited, so a dead collector can't feed errors back into the log exporter. "Forward to Claude Code" adds `CLAUDE_CODE_ENABLE_TELEMETRY` + `OTEL_*` to the `claude` spawn in `CliProvider` (read via `currentOtelConfig()` so that module doesn't import the SDK). The OTel/gRPC packages are in `serverExternalPackages` in `next.config.ts`.

Beyond that, three more sources feed it. **Outbound HTTP**: `src/lib/otel-preload.ts` enables the undici (`fetch`) and `http` instrumentations for CLIENT spans, which are what a backend's service map draws edges from. It must stay the *first* import in the worker and integrations entry points, because the `http` instrumentation only catches modules that load after it. **Database metrics**: every Prisma client is wrapped by `withDbTelemetry()` (`src/lib/db-telemetry.ts`), which gives `db.client.operation.duration` for every query and a warning log for queries over 500ms; the worker adds SQLite file-size gauges. **Database spans** (Settings toggle, off by default): `@prisma/instrumentation`, switched on and off live in `syncPrismaInstrumentation()`. The tracer's sampler (`shouldRecordSpan()`) drops Prisma spans with no parent, which are background polling; that's also why the live-log SSE loop runs inside `detachFromTrace()`.

**GenAI (LLM) telemetry** follows the `gen_ai.*` conventions so GenAI backends (e.g. ObiStack's AI Observability pages, which read traces only) can show model calls, tokens, cost and cache use. The rule that matters: those backends count *every span that names a model* as a model call and sum its `gen_ai.usage.*`, so each unit of model work carries usage on exactly one span. The worker emits one `invoke_agent <agent>` span per agent run via `withAgentSpan()` (`src/worker/telemetry.ts`) — named after the task title (`gen_ai.agent.id` = task id), since GenAI backends name a run after its agent; a team task's span carries no model or usage and its members are `invoke_agent <member>` sub-agents that do — carrying the run's aggregate usage, cache tokens and answering model from the provider's `ExecutionResult` (`cacheReadTokens`/`cacheCreationTokens`/`model`; Codex doesn't report cache yet), `error.type`, and `gen_ai.conversation.id` = task id. `task.run` therefore uses `ctm.task.model`/`ctm.task.*_tokens`, never `gen_ai.*` usage. Tool calls are `execute_tool <tool>` children: the API providers' in-process tools via `executeTool()` (`src/lib/providers/tools.ts`), and the Claude CLI's (which run inside the CLI) rebuilt from its stream by `ToolSpanTracker` (`src/lib/providers/tool-spans.ts`) — opened at `tool_use`, closed at the matching `tool_result`; Codex's aren't traced yet. A failed call's span status carries a content-free message from the pure `describeToolError()` (`src/lib/tool-error.ts`, unit-tested) — `Exit code N` (also `process.exit.code`), a timeout/permission/interrupt, or the first line of the CLI's own `<tool_use_error>` — never the tool's output. With Settings → Observability → "Record tool call arguments" (`otel_tool_arguments`, off by default, read per call via `currentOtelConfig()`), each `execute_tool` span also gets `gen_ai.tool.call.arguments`: the pure `toolCallArguments()` (`src/lib/tool-arguments.ts`, unit-tested) keeps a per-tool allow-list (Bash command + description, file paths, patterns, URLs — never contents, edit strings or prompts) and runs `redactSecrets()` over it. That opt-in is the one exception to the no-content rule below; extend the allow-list there, not at the call sites. `gen_ai.response.finish_reasons` carries only the model's own stop reasons (`ExecutionResult.finishReasons`; the CLI reports just the final turn's), never invented ones, so truncation queries (`max_tokens`/`length`) stay truthful. Each LLM gateway request is a `chat <model>` span (`GatewayCall`, `src/lib/llm-gateway/telemetry.ts`) ended when a streamed response finishes, tagged with the API key. Both record `gen_ai.client.operation.duration` and `gen_ai.client.token.usage` (`src/lib/gen-ai-otel.ts`). Prompt/response content is never recorded. Usage extraction and error classification are the pure `src/lib/gen-ai-telemetry.ts` (unit-tested); a refusal is `error.type=refusal` and a provider content-policy block `content_filter`, which is what "blocked prompt" queries look for. Quality is reported as `gen_ai.evaluation.result` log events (`recordEvaluation()`, `event.name` set): `task_outcome` from `traceTaskRun()` (completed/no_changes = 1, failed = 0; retries, pauses and kills aren't verdicts) and `human_review` via `recordTaskReview()` (`src/lib/task-evaluation.ts`) on approve (PATCH `reviewStatus: "done"`, MCP `review_task`) = 1, PR merged (pr-sync) = 1, request changes = 0. A review comes long after its run's trace ended, so `traceTaskRun()` saves the `task.run` span's ids on the task (`Task.telemetryTraceId`/`telemetrySpanId`) and `recordTaskReview()` parents the event on them (validated by the pure `savedSpanContext()`), which puts the score in that run's trace. We don't run LLM judges.

**Provider auth failures** (expired OAuth login, revoked API key, expired Codex login) are emitted as an error-level `ctm.provider.auth_failure` log event plus a `ctm.provider.auth_failures` counter by `recordProviderAuthFailure()` (`src/lib/provider-auth-otel.ts`; pure attributes/redaction in `src/lib/provider-auth-telemetry.ts`, unit-tested). Attributes: `ctm.provider.id`/`name`/`type`, `gen_ai.provider.name`, `error.type=authentication`, `ctm.provider.auth.source` (`task_run` — the worker's auth-failure hand-off; `credential_check` — the worker's periodic CLI probe; `health_check` — the health page), `ctm.provider.auth.reason` (credential-shaped strings masked) and `ctm.task.id` when there is one. Unlike the email it has no cooldown: it fires every time a dead login is seen.

Naming: emit the current OTel semantic conventions (`server.address`, `db.system.name`, `db.query.text`, `gen_ai.request.model`, `gen_ai.usage.*_tokens`, `gen_ai.provider.name`, `gen_ai.operation.name`) and prefix anything app-specific with `ctm.` (`ctm.task.id`, `ctm.provider.name`, …). Don't add deprecated aliases such as `db.system`; mapping old names is the backend's job.

### Providers (`src/lib/providers/`)

Provider types (`AIProviderType` in `src/lib/types.ts`, constructed by `createProvider()`): `cli`, `api`, `openai`, `claude-pki`, `codex-cli`.

- `CliProvider` — spawns `claude`, using the user's local Claude subscription
- `ApiProvider` — spawns `claude` with `ANTHROPIC_API_KEY` and `--model`
- `CodexCliProvider` — spawns `codex exec`, using the user's ChatGPT/Codex login

All accept a `cwd` argument (the workspace path) so the agent auto-loads `CLAUDE.md` files from cloned repos.

**"Disabled" means never used, by anything.** `isEnabled: false` is an unambiguous "don't use this connection", and every path honours it: `getProvider()` falls through a disabled explicit pin, `pickSmartProvider()`/`findAlternateProvider()`/`findSoonestThrottledProvider()` only ever consider enabled rows, and Slack's `pickProposalProvider()` refuses to return one. Two subtler places had to be brought in line, because "used" isn't only "ran a task":

- *Health checks.* Disabled `cli`/`codex-cli` connections are still **listed** on the health page (their usage stats are worth seeing) but no longer **exercised**: `checkCliProvider`/`checkCodexCliProvider` skip the liveness prompt and the credential write for anything disabled (`DISABLED_SKIP_REASON`), and the route skips the credential sync-back for them. Usage figures still come through — Claude's from an HTTP call against the stored token, Codex's from a local rate-limit file — neither of which spends the subscription.
- *Shared config dirs.* Both CLIs authenticate from a file in a config dir (`~/.claude/.credentials.json`, `$CODEX_HOME/auth.json`), so two connections that leave `configDir` blank share one login file. The old rule — "don't overwrite an on-disk copy with a later expiry", meant to protect a token the CLI had just rotated — read across connections as "keep whatever is there", so a task could run on the account of a provider that was switched off, and the sync-back then copied that account onto the running provider's row for good. `src/lib/providers/cli-credentials.ts` now owns both directions: a marker file (`.task-manager-provider`) records which provider a dir currently holds the login for, `decideCredentialWrite()` (pure, unit-tested) lets *identity beat freshness* — a dir owned by someone else is overwritten, a dir owned by us keeps the rotation — and `canAdoptDiskCredentials()` gates every disk→DB sync so one account can't be copied onto another provider. Dirs with no marker (installs predating it) keep the old expiry guard unless the bytes on disk are exactly another connection's stored login.

**Signing in from the UI.** A `cli` provider can be (re)authenticated from Settings → AI ("Sign in with Claude" in the provider form, and a "Sign in" button on any row whose cached health check says `authStatus` is `error`/`missing`). It runs the real CLI — `claude auth login --claudeai`, which works without a TTY: it prints the sign-in URL and reads the `code#state` the user pastes back from stdin — with `CLAUDE_CONFIG_DIR` set to a throwaway temp dir, then stores the `.credentials.json` it writes via `saveProviderCredentials()` (DB + config dir + owner marker, and clears `authFailureNotifiedAt`) and re-checks just that provider (`refreshProviderHealth()`). The live process sits in an in-memory session map between the two requests (`POST /api/providers/[id]/login` → URL, `POST …/login/[sessionId]` → code), so it assumes a single app replica. Pure helpers are `src/lib/providers/claude-login.ts` (unit-tested), the runtime `claude-login-runtime.ts`. On macOS the CLI may keep its login in the Keychain instead of the file, in which case the flow reports that it couldn't read the credentials; Linux hosts (the Docker/Helm deployment) write the file. Each instance of the task manager needs its *own* login: OAuth refresh tokens rotate on use, so two instances sharing one login keep invalidating each other.

**A dead login hands the task off, it doesn't fail it.** When a run dies because the provider can't authenticate (`Failed to authenticate: OAuth session expired and could not be refreshed`, a revoked API key, an expired Codex login), the provider returns `authFailed: true` on its `ExecutionResult` and the worker treats it like a rate limit: it logs the reason, sends the provider-auth-failure notification (24h cooldown via `authFailureNotifiedAt`), and moves the task to `findAlternateProvider()` as `pending` with `retryCount` bumped, so the next run resumes in the existing workspace. The providers that failed for a task are remembered in memory, so it never bounces back to one of them. With auto-switch off, or no other usable provider, it fails as before. Detection (`src/lib/auth-failure.ts`, unit-tested) only looks at diagnostic output: stderr, error events and the last few lines of a failed run. Codex uses `detectCodexAuthError()` over its fatal lines only. That way an agent that merely writes about 401s can't take a connection out of rotation.

The UI matches: a task pinned to a since-disabled provider shows the connection that will actually run it (task detail page and `GET /api/tasks`), not the switched-off one.

**Codex (`codex-cli`)** — every code path that shells out to `codex` goes through `src/lib/providers/codex-exec.ts`, and nothing else may spawn the binary directly. It owns the things that used to be easy to get inconsistently wrong:

1. *Finding the binary.* `codex` is often installed somewhere a systemd/Docker service's `PATH` doesn't cover, which is what "Codex CLI not found" almost always means. `findCodexBinary()` probes the usual install dirs (plus `CODEX_PATH`), `codexCommand()` spawns the absolute path it found, and `codexEnv()` hands the child the augmented `PATH` too.
2. *Auth.* Codex keeps `auth.json` in `CODEX_HOME` (default `~/.codex`), not `~/.claude/.credentials.json`. `writeCodexAuth()` (via `syncCredentialsToDisk()`) pushes the DB copy to disk before a run and the caller syncs any refreshed copy back afterwards — skipping the sync burns the rotated refresh token. There is no `expiresAt` field, so `extractCodexExpiresAt()` reads the `exp` claim out of the JWT; **0 means "unknown", never "expired"**.
3. *Output.* `codex exec --json` is a JSONL thread-event stream, not Claude's format. `parseCodexEvent()` is the single parser — it emits only `item.completed` (the same item also streams as `started`/`updated`), and reads token usage off `turn.completed`.
4. *Flags.* `codexExecArgs()` builds them. Task runs get `--dangerously-bypass-approvals-and-sandbox`; every assistant/chat helper gets `--sandbox read-only`, which is Codex's equivalent of the `--tools ""` guarantee the Claude helpers rely on. Effort goes through `codexReasoningEffort()`, which clamps our `xhigh`/`max` rungs to `high` because Codex rejects anything else.
5. *Which errors actually mean the run failed.* Codex is loud about problems it is already handling, and taking all of it at face value is what produced the nonsensical `Task failed: Codex CLI exited with code 0`. `classifyCodexFailure()` sorts every error line into three buckets and everything downstream keys off it: **recoverable** (`apply_patch verification failed`, `invalid patch: multiple operations target …` — Codex hands these back to the model, which re-reads the file and retries, so they are logged and counted but never fail a run), **transient** (WebSocket resets, `failed to lookup address information: Try again`, idle timeouts, `failed to refresh available models`) and **fatal** (everything else). Consequences worth knowing: `parseCodexEvent()` only sets `failed` for the fatal bucket; Codex's stderr `tracing` output goes through `classifyCodexStderr()` so its ERROR-level chatter is logged at *system* level; the usage-limit detector is run only over non-transient lines, because a DNS "Try again" would otherwise read as a plan reset and throttle the provider for an hour; and a transient line only condemns a run when no `turn.completed` ever arrived (`Reconnecting… 2/5` is also printed for blips Codex survives).

   Three plumbing rules make that classification actually hold at run time, and breaking any of them re-introduces spurious errors:

   - *Classify whole lines only.* A `data` event is not a line. Codex's stderr routinely splits a tracing line across chunks, and half of `…error=apply_patch verification failed…` classifies as **fatal** — red errors in the log for a healthy run, and a failed task instead of a retry. Both streams go through `createLineBuffer()`, and whatever the stream ends without a newline is flushed on `close` (that trailing line is usually the interesting one). Both handlers also stop once the attempt is settled, so a killed process can't append to a task the worker has already moved on from.
   - *Usage limits are read off diagnostics, never the transcript.* A match throttles the whole connection for up to an hour, so the detector may only see lines Codex itself produced — error events, plain-text warnings, stderr tracing (`isDiagnostic` on `CodexEvent`). It used to run over every line of output, which meant an agent that wrote "added rate limiting" or printed a diff touching line 429 took the provider out of rotation. `detectCodexUsageLimit()` is correspondingly narrow: bare `rate limit`, bare `try again in …` and a bare `429` no longer match. `CodexSignalTracker` owns this, along with the rest of a run's signals (bounded, so a long noisy run can't grow an array forever).
   - *A completed turn only excuses a wobble that came before it.* `sawTurnCompleted` means "a turn completed **since** the last transient problem". Any turn ever completing used to be enough, so a run whose stream died half way through reported success and the task was marked complete with the work unfinished.

   When a run does die transiently, `CodexCliProvider` re-spawns `codex exec` — Codex's own five reconnects are gone by then, so recovery means a fresh process. Up to `CODEX_MAX_ATTEMPTS` (3) with `codexRetryDelayMs()` backoff, all inside the task's *single* time budget, and each retry prepends `codexResumeNotice()` telling the model that the workspace already holds the previous attempt's work and to continue from it rather than start over. `runCodexText()` retries the same way (and returns a partial answer rather than throwing when Codex exits non-zero after the model already replied), and `probeCodexLiveness()` probes twice before the health page is allowed to blame the connection for what is really a network blip.

6. *Killing it.* Task runs bypass the sandbox, so `codex exec` shells out to installs, builds and test suites; signalling only the `codex` pid on a timeout or a cancelled task left those running, burning CPU and holding the workspace open against the cleanup that follows. Every Codex child is therefore spawned `detached` (its own process group) and killed through `killCodexProcessTree()`, which signals the group and falls back to the single process. `trackCodexChild()` registers each live child so a worker shutdown (`SIGINT`/`SIGTERM`/`SIGHUP`/`exit`) sweeps them up rather than orphaning them; the handlers re-raise the signal so shutdown is not swallowed.

**Smart picker ranking** (`pickSmartProvider()`): Claude subscriptions are ordered by when their *weekly usage window renews* (read from the OAuth usage API, cached 60s per connection, injectable via `usageLookup` for tests), soonest first, so capacity about to be reset is spent rather than lost; on an exact renewal tie the higher remaining percentage wins, and accounts whose usage is already spent are skipped. The ordering itself is the pure `rankProvidersForSmartMode(providers, now)` (unit-tested) — `pickSmartProvider()` only gathers its inputs. It deliberately does **not** rank by the stored OAuth access-token `expiresAt` — that token rotates every few hours and says nothing about capacity — which is only a tiebreak for subscriptions with no usage figures. An expired stored access token never removes a connection from the pick (the CLI refreshes it; a genuinely dead login goes through the auth-failure hand-off). Metered API providers come last.

**Usage cap** (`AIProvider.maxUsagePercent`, default 100 = none): a subscription connection (`cli`, `codex-cli`) can be limited to a share of each plan window so the task manager leaves the rest for the user's own manual use — e.g. 90 keeps 10% free. Set from the provider form in Settings → AI; `POST`/`PATCH /api/providers` accept it (whole number 1–100). It reuses the throttle machinery instead of adding a parallel one: once the 5-hour or weekly window reaches the cap, the provider gets `throttledUntil` = that window's reset, so every selection path already handles it. Enforced in four places — the smart picker skips over-cap accounts (`isUsageExhausted(…, cap)`), the worker's `getProviderWithinUsageCap()` runs `enforceUsageCap()` (`src/lib/usage-cap.ts`) on the provider it's about to use at pre-flight and pre-spawn, the periodic Claude usage check throttles over-cap accounts and won't clear that early, and `revalidateProviderThrottle()` keeps a cap throttle in place while the window is still over. Usage credits never override a cap. It's checked at pick-up, not mid-run, so a long run that starts just under the cap can end above it.

Codex is in the *subscription CLI tier* of the smart picker (`isSubscriptionCliType()` in `src/lib/smart-provider.ts`) alongside `cli`, so it is preferred over metered API providers and `calculateCost()` returns `null` for it. Because a smart pick or throttle fallback can move a task between vendors, the worker drops a task model that doesn't fit the provider actually running it (`modelFitsProvider()`) rather than sending `claude-opus-5-5` to `codex exec`.

When adding a provider type, the checklist is: `AIProviderType` → `createProvider()` → `checkProvider()` in `src/lib/health-check.ts` (otherwise the health page reports "Unknown provider type") → the smart picker's tiering → `getModelsForProviderType()` → `calculateCost()` → and the CLI branch of each assistant route in `src/app/api/tasks/*` plus `src/lib/chat.ts`, `src/lib/repo-chat.ts` and `src/integrations/slack.ts`, all of which otherwise fall through to spawning `claude`.

### Prompt construction (`src/lib/prompt-builder.ts`)

`buildPrompt()` assembles the full system prompt + task metadata. The task's `context` field is the right place for per-task instructions that shouldn't live in the repo's `CLAUDE.md`. On retry (`retryCount > 0`), a resume section is added telling Claude to continue from existing work.

### Task lifecycle

`pending` → `running` → `completed` | `failed` | `paused` (rate-limited, will retry at `nextRetryAt`) | `awaiting_approval` (team pipeline waiting on a human; approving re-queues it as `pending`)

**Repos are cloned at run time, and resumes re-sync with the base.** A first run always clones fresh from the task's base branch (repo branch, else Settings → Git default). A resumed run (`retryCount > 0` — rate-limit pause, auto-retry, re-run from the backlog) reuses the old workspace, so for agent branches `pullAndSyncWorkingRepo(git, branch, baseBranch)` also rebases onto the *latest* `origin/<base>` via `syncWithBaseBranch()`; otherwise a task cloned days ago would build on a stale base and its PR would conflict. On conflicts it aborts (never leaves a rebase in flight) and the worker appends a "Base Branch Has Moved" section to the prompt context asking the agent to rebase. Tasks on `targetBranch`/`pushToMain` only pull their own branch.

The `TASK_COMPLETE_MARKER` (`---TASK_COMPLETE---`) in claude's output is how the worker detects successful completion.

**Push & PR guarantees.** After the agent runs, the worker commits, pushes, and then *verifies* origin's branch contains the local HEAD (`verifyBranchPushed()`); a push that didn't land fails the task. Whether to open a PR is decided by the pure `decidePrAction()` (`src/lib/pr-decision.ts`, unit-tested), which also counts commits ahead of the PR base (`countCommitsAheadOfBase()`) so a retry whose work was pushed by an earlier run still gets its PR. When a PR was requested and the branch has work, a missing git token or a PR API error fails the task (with `prError` set) instead of letting it pass as `completed`; an already-open PR for the branch is adopted rather than duplicated. On the board, a `no_changes` task with no open PR is always in Done (`hasNothingToReview()` in `src/lib/kanban-column.ts`), even if a stale `reviewStatus: "in_review"` survived a retry.

**Hidden To Do cards.** `Task.hiddenOnBoard` lets the user tuck "not now" To Do cards out of the board: "Hide from board" in a card's detail dialog, or select cards (shift-click / the column's "Select all") and use the header's "Hide N" / "Unhide N" buttons (`POST /api/tasks/bulk-hide` `{ ids, hidden }`; `hiddenOnBoard` is also accepted by `PATCH /api/tasks/[id]`). Board Settings → "Show hidden tasks" (localStorage `kanban-settings.showHiddenTasks`, off by default) — or the To Do column's "N hidden" chip — shows them dimmed with a "Hidden" badge. It is display only: the worker ignores it, so a hidden *queued* task still runs. `isHiddenOnBoard()` (`src/lib/kanban-column.ts`, unit-tested) only hides cards in To Do, so a hidden task reappears as soon as it runs. Reordering To Do reorders the full queue, hidden cards included.
